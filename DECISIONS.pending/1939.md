### `business-cockpit-bom` names the cockpit's own artifacts and imports only the VanillaBP BOM

This changes decision 86. Decision 86 stays for the BOM itself, its parent and what it costs, but
the BOM no longer imports `spring-boot-dependencies` and `spring-cloud-dependencies`. Mark decision
86 with an addendum which names this entry.

#### What was found

`business-cockpit-bom` imported the BOMs of Spring Boot and Spring Cloud. So it was wrong in a
Quarkus application: the Spring versions would have won over the ones `quarkus-bom` brings. The
wiki, the README files and the upgrade skill had to tell every workflow module on Quarkus not to
import it, and to name the version of each cockpit artifact itself. `io.vanillabp:vanillabp-bom`
imports no BOM of a framework and fits both platforms. Most libraries do the same: the BOMs of
Testcontainers, Jackson and Spring Cloud do not import the Spring Boot BOM either. The application
decides which framework version it runs.

No build relies on the Spring versions of the BOM. Neither this repository (the root `pom.xml`
imports the Spring BOMs itself, and `container` inherits them), nor the five adapter repositories
`business-cockpit-*`, nor the blueprints import `business-cockpit-bom`. Only a derived cockpit
application does, as the wiki page "Building a custom Business Cockpit" and the skill
`business-cockpit-creator` describe it.

#### The decision

- `business-cockpit-bom` imports `vanillabp-bom` and names `mongodb-changesets` and every published
  artifact an application or a workflow module builds against, now with
  `official-gui-api-quarkus-client`. It imports no BOM of Spring Boot, Spring Cloud or Quarkus.
- An application chooses its framework versions itself. A derived cockpit takes
  `spring-boot-starter-parent` as its parent or imports `spring-boot-dependencies`, on the Spring
  Boot line the cockpit is built with: the version of `spring-boot-dependencies` in the root
  `pom.xml`. A workflow module on Quarkus imports `quarkus-bom`. Both import `business-cockpit-bom`
  as well.
- Spring Cloud is there for one reason: the proxy of the library under `/wm/` is
  `spring-cloud-starter-gateway-server-webmvc`. Its version lives in the root `pom.xml`, which
  imports `spring-cloud-dependencies`. The published POM of `business-cockpit` inherits that import
  from `business-cockpit-parent`, so an application gets the gateway in the version the cockpit is
  built with, without an import of its own. An application which uses Spring Cloud for something
  of its own imports `spring-cloud-dependencies` itself, in the release train which fits its Spring
  Boot.

#### What it costs

A derived cockpit names one more thing: its Spring Boot parent or its import of
`spring-boot-dependencies`. Without it the starters have no version and the build stops with a
message which says so, so nobody runs on the wrong versions by accident. The version of Spring Boot
is no longer written twice in this repository: `bom/pom.xml` keeps only `version.vanillabp` and
`version.mongodb-changesets` next to the root `pom.xml`.
