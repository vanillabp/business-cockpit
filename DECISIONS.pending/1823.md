# A snapshot carries no sources, javadoc only where somebody builds against it, and waits when Central asks

Decided on 2026-11-12 by the maintainer.

## What was found

The publish of `main` sends every snapshot to the snapshot repository of Maven Central in one go,
at the end of the reactor. Central answered some of those requests with `429 Too Many Requests`,
and the publish failed five times in a row. The monthly limit of the Central Portal counts releases
only, so this is a limit of requests per time. Starting the publish again by hand sends every file
again, which is the most expensive way to repeat it.

A snapshot sent more than it needed. The root POM attached a sources jar in every build, so every
module went out with one, and the simulator went out although nothing builds against it.

## The decision

A snapshot carries no sources jar. The sources jar belongs to a release, where Maven Central asks
for it and where the line numbers of a stack trace have to match the code.

A snapshot carries a javadoc jar only for the modules which an application or an adapter builds
against. These modules set the property `skip.javadoc.jar` to false:

- `spi-for-java` and `support`, which a workflow module names
- `business-cockpit`, the library a custom cockpit is built from
- the four modules of the extension, `extensions-commons`, `extensions-commons-spring-boot`,
  `extensions-commons-quarkus` and `extensions-commons-quarkus-deployment`, which the five adapters
  build on
- the generated clients, `bpms-api-client` and `workflow-provider-api-client`

Every other published module goes out as a snapshot with its jar and its POM only: `container` and
`dev-shell-simulator` (an application, read as a runnable jar), the generated servers
`bpms-api-server`, `workflow-provider-api-server` and `official-gui-api-server`,
`bpms-protobuf-api`, and `extensions-commons-test-support`, which the adapters use in their tests
only.

A release still carries a sources jar and a javadoc jar for every module it publishes. The profile
`release` of `io.vanillabp:release-parent` binds both, and the profile `release` of the root POM
sets `skip.javadoc.jar` to false. A module which has no code to document, like
`test-coverage-report` and `development/workflow-module-on-support-only`, sets the property to true
itself, because the profile cannot overrule a value a module sets.

The javadoc check stays in every build and every module. It is the execution `check-javadoc` of
the parent, and it does not depend on the jar. So a javadoc error still fails the pull request, and
not only the release.

What nothing builds against is not published. Before a module is taken off Maven Central, the five
adapter repositories and the blueprints are searched for its coordinates, and what anybody uses
stays published. Today that takes off `development/simulator` only. Its runnable jar is still
attached to every GitHub release.

A request which Central refuses with 429 or 503 is repeated on its own, after a pause, and the build
goes on. `.mvn/maven.config` sets this for the HTTP transport of Maven Resolver 1.9, which is the
one in Maven 3.9:

|                        property                         |   value   |                             what it means                             |
|---------------------------------------------------------|-----------|-----------------------------------------------------------------------|
| `aether.connector.http.retryHandler.count`              | `8`       | how often one request is repeated                                     |
| `aether.connector.http.retryHandler.interval`           | `15000`   | the pause before repeat n is n times this, in milliseconds            |
| `aether.connector.http.retryHandler.intervalMax`        | `120000`  | a longer pause, also one asked for by `Retry-After`, ends the repeats |
| `aether.connector.http.retryHandler.serviceUnavailable` | `429,503` | the answers which are repeated                                        |

The resolver reads the header `Retry-After`, as seconds or as a date, and waits that long instead
of its own pause. Without the header, one request waits 15, 30, 45 and so on up to 120 seconds, 9
minutes for all eight repeats. With the header, it is at most eight times two minutes. Without the
file, the resolver repeats three times within 30 seconds. The file applies to every build, on a
laptop and in a pull request as well, and that is meant.

## What it costs

A developer who opens a class of a snapshot in the IDE sees decompiled code and no sources. The
IDE still shows the javadoc of the modules listed above. A released version has both.

A pull request builds the javadoc jar of the modules listed above in every build, a few seconds
each.

A new module goes out as a snapshot without a javadoc jar until it sets the property. A module
which an application or an adapter builds against has to set it.

## Where it applies

- `pom.xml`: the property `skip.javadoc.jar`, the execution `attach-javadocs` of
  `maven-javadoc-plugin` and the profile `release`. The binding of `maven-source-plugin` is gone.
- the property `skip.javadoc.jar` set to false in `spi-for-java/pom.xml`, `support/pom.xml`,
  `business-cockpit/pom.xml`, `extensions-commons/core/pom.xml`,
  `extensions-commons/spring-boot/pom.xml`, `extensions-commons/quarkus/runtime/pom.xml`,
  `extensions-commons/quarkus/deployment/pom.xml`, `apis/bpms-api/client/pom.xml` and
  `apis/workflow-provider-api/client/pom.xml`
- the property set to true in `test-coverage-report/pom.xml` and
  `development/workflow-module-on-support-only/pom.xml`
- `development/simulator/pom.xml`, `skip.central.release`, and `development/simulator/README.md`
- `.mvn/maven.config`
- `README.md`, the paragraph on what a snapshot of `main` carries
