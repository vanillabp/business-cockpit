### The module `container` logs a person in by OpenID Connect at the simulator, and the login still ends in the JWT cookie

Decided on 2026-11-11 by the maintainer: OpenID Connect comes into `container` before 1.0, and the
token stays the cockpit's own JWT in a cookie. Moving to the mechanisms of Spring Boot, with a
resource server and the token in a header, changes what an upgrade costs, so it comes after 1.0.
The questions below took their defaults.

#### What was there

Decision 76 moved the login out of the library into `container`. There it asked for HTTP basic,
and every user had the password `test`. That is a login nobody runs in production. A real cockpit
logs in at an identity provider, and `container` did not show how. The wiki showed an
`oauth2Login` chain, and no test proved it. It did not work: the line which should write the
login into the JWT cookie had no effect, see below.

#### The decision

1. The simulator of `development/simulator` plays the OpenID Connect provider. It is Spring
   Authorization Server, which is a module of Spring Security since version 7. Its persons are the
   users of `dev-shell-simulator.users`, and each logs in with `test` at a login form. The
   provider lives in the simulator and not in the dev-shell simulator, because every workflow
   module needs the dev-shell simulator but not every project has OpenID Connect (decision of the
   maintainer on 2026-10-29). The cockpit already loads its users from the simulator, so a
   developer starts no process more than before.
2. The profile `local` of `container` logs in with `oauth2Login` at the simulator. The endpoints
   of the provider are named one by one, without `issuer-uri`. With an issuer, Spring Boot asks the
   provider while the application starts, and the cockpit would depend on the start order.
3. HTTP basic stays, as the profile `basic-auth`. The integration tests use it, a script can use
   it, and a developer who runs only the dev-shell simulator needs it. The two chains are nested
   configurations of `GuiSecurityConfiguration`, each with the bean name `guiHttpSecurity`, and the
   profile decides which one exists.
4. The login ends in the JWT cookie `bc`, through `JwtSecurityContextRepository`. The token is the
   same as with HTTP basic. Its subject is the claim `sub` of the provider, which is the id of the
   user in `dev-shell-simulator.users`, so the user directory knows the user by it (decision 87).

#### What the reference project taught

An application built on an older cockpit logged in the same way: a simulator derived from the
dev-shell simulator played the provider, and the cockpit logged in with `oauth2Login` and kept the
login in its own cookie. Four details come from there or turned up while building this:

- The simulator ends its session once it has issued the code. So the next login asks for a user
  name and a password again. A developer can switch to another user, and a logout at the cockpit is
  not undone by a session still open at the provider.
- The simulator names its session cookie `SIMULATOR_SESSION`. A browser sends a cookie to every
  port of a host. With the default `JSESSIONID`, the login at port 8079 replaced the session cookie
  in which the cockpit at port 8080 keeps the login it started, and the cockpit could not finish
  it.
- A request to the GUI API or the BPMS API without a login gets 401, and only a page gets the
  redirect to the provider. A `fetch` of a user interface or a BPMS adapter would follow the
  redirect and fail at the provider.
- The cockpit sends PKCE (proof key for code exchange), although it has a client secret. Spring
  Security adds PKCE on its own only for a client without a secret, and Spring Authorization Server
  asks for it from every client by default. The current advice for OAuth is PKCE for every client.

The overview of rights of the reference project is decision 99 and needs nothing here.

#### `securityContextRepository` of `oauth2Login` has no effect

`oauth2Login(login -> login.securityContextRepository(repository))` looks like the way to write the
login into the cookie. Spring Security 7.1 sets that repository on the login filter, and then,
while it builds the chain, replaces it with the repository of the whole chain. That one keeps the
login in the HTTP session. The browser notices nothing. But no cookie `bc` is written, so a
workflow module behind the proxy gets no user, and `JwtRenewalFilter` has nothing to renew.

`GuiSecurityConfiguration` sets the repository with an `ObjectPostProcessor` of the
`OAuth2LoginAuthenticationFilter`. Spring Security runs it after the replacement. Setting the
repository of the whole chain with `securityContext(..)` would work as well, but then every request
decodes the cookie twice, once there and once in `PassiveJwtSecurityFilter`.
