### `support` has one module per platform, and the Spring Boot one carries the exceptions of a user task

This entry changes the artifact which decisions 83, 84 and 86 name. What they say about the content
of `support` stays true.

#### What was found

A Quarkus version of `support` will follow. Its classes check a login and answer a request in the
way Quarkus does it, so it cannot be the same artifact as the Spring Boot one. With a single module
named `support`, the second one would have needed a new name next to it, and the old name would
have kept meaning Spring Boot.

Every workflow module with forms of its own also needs to say two things to the form: the task id
does not belong to the workflow, and the task is no longer open. The blueprints wrote the same two
exceptions and the same handler for that in each module.

#### The decision

`support` is a parent POM, artifact `support-parent`, with one module per platform below it. The
names follow `extensions-commons`, where the parent is `<directory>-parent` and a platform module
lives in a directory named after the platform. Today there is `support/spring-boot`, published as
`io.vanillabp.businesscockpit:business-cockpit-spring-boot-support`. A Quarkus module joins later as
`support/quarkus`. The Java packages stay `io.vanillabp.cockpit.support...`, so the move changes no
import.

The artifact `io.vanillabp.businesscockpit:support` is gone, and no artifact under the old name
points at the new one. It was published only as a 0.9.0 snapshot. `business-cockpit-bom` manages
`business-cockpit-spring-boot-support` in its place.

The Spring Boot module gets the package `io.vanillabp.cockpit.support.usertask` with
`BcUnknownTaskException`, `BcTaskNotOpenException` and `BcUserTaskExceptionHandler`. The prefix
`Bc` follows `BcUnauthorizedException`, the exception which was in `support` before. The handler is
a `@RestControllerAdvice` which answers `404 Not Found` and `409 Conflict`, with the message as
plain text so a form can show it.

The handler is a class of its own and not a `@ResponseStatus` on the exceptions. With
`@ResponseStatus`, Spring Boot answers with its error page and leaves out the message, unless the
application sets `server.error.include-message`. `BcUnauthorizedException` carries no annotation
either. The cockpit's `RestfulExceptionHandler` answers it, and a workflow module does not have
that handler, so the new exceptions bring their own.

Nothing in `support` registers the handler, the same as `UserContextConfiguration`. A workflow
module imports it with `@Import(BcUserTaskExceptionHandler.class)`, or its component scan reaches
it. The library imports it in `BusinessCockpitGuiApiAutoConfiguration`, next to
`UserContextConfiguration`, because `EveryCockpitBeanIsRegisteredTest` asks that every component
below `io.vanillabp.cockpit` is reached by an auto-configuration. The cockpit throws neither
exception itself, but a controller of a derived cockpit which throws one answers like a workflow
module does.

#### What it costs

Every build which used the 0.9.0 snapshot of `support` changes one `artifactId`, see `UPGRADE.md`.
The adapter repositories and the blueprints name the old artifact and break when the next snapshot
of this repository is published, until they change it.
