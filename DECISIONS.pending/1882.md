### A Quarkus workflow module without quarkus-security builds and starts, and its user context reads any login

This entry changes decision 104, which gave the Quarkus module of `support` its own check of the
cockpit's login token.

#### What was found

`UserContext` injected `SecurityIdentity`. Only the extension `quarkus-security` makes that bean,
and the module names the extension as optional. So a workflow module which had `support` only for
the SPI and the exceptions of a user task, with `quarkus-rest` but without `quarkus-security`, did
not build: ArC refused the injection point. The build property `business-cockpit.jwt.enabled=false`
did not help, because it left out the mechanism, the provider and the start check, but not the user
context.

ArC has no condition on a class or an extension which a library could put on a bean. Only an
extension with a build step could, and `support` is a plain jar on purpose. `quarkus-rest` brings
the HTTP layer and the API classes of Quarkus security, but not the beans of `quarkus-security`.
The mechanism and the identity provider are beans nobody asks for without that extension, so ArC
leaves them out.

#### The decision

`UserContext` and `JwtStartupCheck` look the beans of `quarkus-security` up with `Instance` instead
of injecting them, so nothing in the module needs a bean of an extension the application may leave
out.

- `UserContext` stays in every application and is not tied to the build property. It reads the
  identity of whatever login the request has. With the check switched off it tells the user of the
  application's own login, the way its javadoc already said. Without `quarkus-security` nobody is
  logged in, so it throws `BcUnauthorizedException`.
- Without `quarkus-security` the start check still refuses keys nobody reads, but it does not ask
  for a secret or a directory: there is no token to check. It writes one line to the log. A secret
  set all the same ends the start, with a message which says to add `quarkus-security` or to remove
  the key and set the build property to `false`.

So the Quarkus extensions are: `quarkus-rest` for the answers to the exceptions, and
`quarkus-security` as well for the check of the login token. `business-cockpit.jwt.enabled=false`
stays the way to leave the check out in an application with `quarkus-security`.

#### What it costs

An application which forgot `quarkus-security` and set no secret starts without a check of the
token. The log line says so, and `@RolesAllowed` is not enforced without `quarkus-security` anyway.
