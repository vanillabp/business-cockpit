# Addendum to decision 88: a change while a registration is on its way is registered again

No new decision and no new number. This is one point added to decision 88 ("The group hierarchy
of a workflow module may come from a bean, and the bean's interface is part of the cockpit's
SPI").

## What was found

A change of the hierarchy got lost now and then. `scheduleRegistration` planned the registration
with plain `schedule`. A plain call is dropped while an entry with the same key has not been
marked DONE, and that includes an entry a dispatch has already taken. So a change which came after
the registration on its way had read the hierarchy, but before that entry was DONE, was dropped.
The cockpit never got the new hierarchy. The test `GroupHierarchyFromABeanTest` on Quarkus hit
this in the CI of business-cockpit#380.

## The line to add

Add this as point 9 under "The decision" of decision 88, after point 8:

```markdown
9. The registration is planned through `PhaseTwoOutbox#scheduleReplacingWhatIsStillWaiting`. A
   waiting registration has not read the hierarchy yet, so the new one takes its place and the
   module still registers once. A registration which a dispatch has taken may have read the old
   hierarchy already. The store never replaces it, so the new one is written beside it and a
   second registration follows. Plain `schedule` would drop the new one against the one on its
   way, and the change would never reach the cockpit.
```

And add `BusinessCockpitExtension` (`scheduleRegistration`) to the line about
`extensions-commons/core` under "Where it applies":

```markdown
- `extensions-commons/core`: `BusinessCockpitConfiguration` (`readAndValidate`, `groupHierarchyOf`),
  `BusinessCockpitExtension` (`registerWorkflowModuleAgain`, `scheduleRegistration`),
  `ConfigurationKeyCheck`
```

## A sentence of decision 26 which is no longer true

Decision 26 says in its paragraph about the registration: "The registration of a workflow module
is planned the old way, with `schedule` and without a payload. [...] A second registration of one
module says what the waiting one says, so keeping the waiting one is right." Since decision 88 the
hierarchy can change, and since this addendum the registration replaces what waits. The paragraph
needs a note such as "Changed by decision 88: the registration replaces a waiting one, see point 9
there." Changing decision 26 needs the maintainer's yes (AGENTS.md), so this is a question for the
merge, not a change of this branch.
