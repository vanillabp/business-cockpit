### REST clients are HTTP service clients, with their keys at the group's prefix

#### What was found

`support` built REST clients with `ClientsConfigurationBase`: OpenFeign and OkHttp, configured
from a properties class the client module binds to a prefix of its choice. Two other ways were
tried against every feature of it. Spring Cloud OpenFeign has no release for the Spring Boot
version the cockpit runs, only fixes bugs, sends the form fields of a generated interface as query
parameters and leaves TLS bundles, proxies and a usable OAuth client to the application. The HTTP
interface clients of Spring Framework 7 (`@HttpExchange`, `@ImportHttpServices`) come with Spring
Boot, and the generator `spring` writes their interfaces with the library `spring-http-interface`.
Spring Boot configures most of a client from keys. Missing are a proxy, `verify-ssl: false`,
retries, logging with bodies, an OAuth client fit for a service, and a check of `base-url` at the
start. Spring Boot reads the keys of a group only below `spring.http.serviceclient.<group>`.

#### The decision

REST clients are HTTP service clients. `support` offers them in the package
`io.vanillabp.cockpit.support.rest.httpservice`, and new clients, the client of the official GUI
API among them, are built this way.

- `HttpServiceClientConventions` configures every HTTP service group of the application, not only
  the groups which ask for it.
- The keys of a group live below one prefix. A client module or an application names it with an
  `HttpServiceGroupPrefix` bean, as it named the prefix of its properties class for
  `ClientsConfigurationBase`. A group without one keeps Spring Boot's place. The prefix starts with
  no `vanillabp`, and `support` fixes no prefix of its own.
- The keys Spring Boot lacks are read at the same prefix: `proxy.*`, `verify-ssl`, `log`,
  `retry.*` and `oauth.*`. Spring Security's own registration keys are not read, so the keys of a
  group stay in one place.
- Two workflow modules of one application may call the same service through the same generated
  interface with different keys. Each imports the interface into a group of its own, with a prefix
  of its own. What the two share, they write twice or bring in a library of their own. A client
  module's own group steps back when the application has groups of that API.
- A caller gets Spring's exceptions, `HttpClientErrorException`, `HttpServerErrorException` and
  `ResourceAccessException`, not Feign's.
- The OAuth client renews a token when a tenth of its lifetime is left, at most
  `oauth.renew-before` before it expires. A token without `expires_in` is kept for
  `oauth.lifetime-without-expires-in`. Token requests use the group's proxy and TLS, and a refused
  one names the key to check. These are settled before 1.0, because the keys are fixed after it.
- Every problem of every group, a key nobody reads included, stops the start in one list.

`ClientsConfigurationBase` stays until the clients built with it have moved.

#### What it costs

Callers of a client which moves change the exceptions they catch, and the keys of
`authentication.*` and the truststore file get new names. `support` brings
`spring-boot-starter-restclient`, and every application with HTTP service groups gets them
checked at the start. A proxy works with the JDK's `HttpClient` only. The JDK drops every
`Authorization` header of a client with an `Authenticator`, so the login for the proxy is sent
with every request, and only Basic is supported.

#### Where it applies

- `support/spring-boot/src/main/java/io/vanillabp/cockpit/support/rest/httpservice`, above all
  `HttpServiceClientConventions`, `HttpServiceGroupPrefix` and `ClientCredentials`.
- `apis/official-gui-api/client/spring-boot`, the first client built this way.
- The section "REST clients" of `support/README.md`, and the section about HTTP service clients in
  `UPGRADE.md`.
- The Quarkus module of `support` and the Quarkus client of the official GUI API follow the same
  rule for where keys live and for two modules with different keys.
