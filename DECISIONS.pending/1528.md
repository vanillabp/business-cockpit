# The names released changesets read are held by a test

## The decision

A released changeset reads some names which are declared outside of it. They keep the values the
changesets were released with. A comment where each name is declared says so, and
`NamesTheReleasedChangesetsReadTest` writes the values down as text and fails when one changes. The
changesets themselves stay as they are.

## Why

The code of a released changeset uses constants and classes from the rest of the cockpit. Renaming
one of them changes what the changeset does on a new database, and not a line of the changeset
changes. Nothing noticed that before.

Writing the values into the changesets as literals would have frozen them in place. That would have
been a change to released changesets, and those are not changed.

## Where it applies

- `UserTask.COLLECTION_NAME`, `Workflow.COLLECTION_NAME`, `WorkflowModule.COLLECTION_NAME`,
  `NotificationOutboxEntry.COLLECTION_NAME`, `User.COLLECTION_NAME`
- `SortIndexes.INDEX_PREFIX`, `UserTaskService.INDEX_CUSTOM_SORT_PREFIX`,
  `WorkflowlistService.INDEX_CUSTOM_SORT_PREFIX`
- `UserTaskEndReason` and `WorkflowEndReason`, the names `COMPLETED` and `CANCELLED`
- `UserTask`: its collection and the fields of `readBy`, `dangling` and `assignee`, because changesets
  update by this class
- `Workflow`: its collection and the field `workflowId`, for the same reason
- `PersonAndGroupMapper.toModelPerson(String)` and `toModelGroup(String)`, which the changesets for
  old records call. The test cannot hold what an application's mapper answers, so only the comment
  does.
- `AGENTS.md`, section "A released changeset never changes"

The new changesets which correct the stored rollbacks of the first changesets write every name out
as text, so they read nothing from outside.
