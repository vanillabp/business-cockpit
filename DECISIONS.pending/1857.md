### A list can be limited to workflow modules, and each wake-up call of the update stream names the workflow module of its entity

#### What was missing

A user interface may show a list which belongs to one business application, for example on a page
of that application. Such a list should hold the user tasks or the workflows of the application's
workflow modules only. The GUI API had no way to ask for that, and the update stream did not say
which workflow module a change belongs to.

#### The limit of a list

Every request of a list takes the optional field `workflowModuleIds`: `POST` and `PUT` of
`/usertask` and `/workflow` on every base path, `POST /usertask/count`, `POST /workflow/count` and
the suggestions of a search field (`OPTIONS /usertask`, `OPTIONS /workflow`). The list then holds
only the entries whose `workflowModuleId` is one of these ids.

- Without the field, with `null` and with an empty array, the list holds the entries of every
  workflow module. A request which does not know the field gets the answer it always got. An empty
  array does not mean "no module", because a list which can never hold anything is no use, and a
  user interface which builds the array from a setting would turn an empty setting into an empty
  list.
- The limit is a filter like `businessIds` and `searchQueries`. It narrows what the visibility of
  the list lets through and never widens it. It is not a permission: a user who leaves it out sees
  everything the visibility allows.
- `POST /workflow/{workflowId}/usertasks` does not read it. The tasks of one workflow all belong to
  the workflow module of that workflow.

The condition is built in one place, `SearchCriteriaHelper.onlyTheWorkflowModules`, and every list
query adds it next to its other conditions.

Two new changesets, one per collection, add an index on `workflowModuleId` followed by `endedAt`, the
same shape as the indexes of the visibility. A database may already hold an index on the same fields
under another name. MongoDB refuses a second one, so the changeset then keeps the index which is
there and stores no rollback.

#### The workflow module in the update stream

The update stream is not limited to workflow modules. Decision 48 says why it cannot be: a request
of a list does not say which tab it comes from, so a stream cannot know which of its lists is
limited. Instead each element of a `UserTask` or `Workflow` event carries `workflowModuleId` next to
`event`, and a list limited to some workflow modules skips the elements of the others.

The module is read in the filtering tick, by the same query which reads the facts of the visibility.
It is not taken from the change event. Decision 31 says that a change event is built without the
document behind it, and an update, giving a task back for example, arrives without one. So
`UserTaskVisibility.TaskFacts` and `WorkflowVisibility.WorkflowFacts` carry `workflowModuleId` as
well, `UpdateStreamAudience.whatEachStreamMaySee` answers with the module of each changed entity
next to the ids each stream may see, and `UpdateStreams` gives every event of that entity its
module. The database still sees one query per tick and kind of entity.

The field is missing in two cases: in a `RELOAD`, which is about no single entity, and when the
cockpit no longer holds the entity. Such an element may concern any list, so a limited list treats
it as one of its own modules.
