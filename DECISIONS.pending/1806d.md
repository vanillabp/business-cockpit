# `support` brings the cockpit's SPI, so a workflow module compiles with `support` alone

Decided on 2026-11-12 by the maintainer. It adds to decision 83.

## What was found

A workflow module behind the cockpit needs two things to compile: the cockpit's SPI, with the
annotations and types for the details of user tasks and workflows, and the user of a request, which
is in `support`. It had to name both artifacts. For `UserDetails`, `support` had only the interface.
The one implementation, `UserDetailsImpl`, was in the library module `business-cockpit`, which
brings MongoDB and Kafka. A team which needed it in the cockpit and in a workflow module had to
build a shared library of its own. `support` exists so that nobody has to do that.

## The decision

`support` depends on `io.vanillabp.businesscockpit:spi-for-java` in compile scope, and not as an
optional dependency. Through it, `support` brings the SPI of VanillaBP, `io.vanillabp:spi-for-java`.
With `support` as its only dependency, a workflow module compiles. To run, it needs the cockpit's
adapter for its BPMS. A workflow module takes the adapter in test scope for its tests, and the
application which runs the workflow module brings it.

`spi-for-java` never depends on `support`.

`UserDetailsImpl` moves to `support`, into `io.vanillabp.cockpit.support.security.usercontext`. The
cockpit and a workflow module both need an implementation of `UserDetails`, so the rule of decision
83 puts it there. No other class of `io.vanillabp.cockpit.users` moves, because a workflow module
does not need them.

The module `development/workflow-module-on-support-only` proves it in every build. It depends on
`support` and on nothing else, and it compiles a workflow service with the annotations of both SPIs
and a class of its own which implements `UserDetails`. It is neither installed nor published.

## What it costs

`support` is no longer free of the SPI. A change to `spi-for-java` is now a change to what `support`
brings, too. An application which names `spi-for-java` itself keeps working, and Maven picks one
version of it.

`UserDetailsImpl` has a new package, one line in `UPGRADE.md`.

## Where it applies

- `support/pom.xml`, the dependency on `spi-for-java` and the description of the module
- `support/src/main/java/io/vanillabp/cockpit/support/security/usercontext/UserDetailsImpl.java`
- `development/workflow-module-on-support-only`, its `pom.xml`, its `README.md` and its classes
- `pom.xml`, the list of modules, where `spi-for-java` now comes before `support`
- `support/README.md`, `spi-for-java/README.md` and `README.md`, section "The modules"
- `UPGRADE.md`, section "`commons` is gone: `support` and the library module take its classes"
- `container`: `LocalUserDirectoryServiceImpl` and the test application `DerivedCockpitApplication`,
  which import `UserDetailsImpl` from its new package
- The wiki pages "Building a custom Business Cockpit" and "Connecting a workflow module"
