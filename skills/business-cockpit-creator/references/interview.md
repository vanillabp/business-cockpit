# The interview

*Part of the description in [`../SKILL.md`](../SKILL.md).*

Ask these questions before you generate anything. Ask every one of them. Where a default is given,
propose it, and let the user decide. Write every answer into `INTERVIEW.md` in the generated
project, with the question id, as soon as the user gives it, see
[How the interview runs](#how-the-interview-runs).

Each question has an id, for example `Q-FOLLOW-UP`. The checklist
[reference-1.0.0.md](reference-1.0.0.md) names these ids, so you can see which items depend on
which answer. Ids are never reused.

## How the interview runs

Before the first question, ask where the UI repository goes, unless the user works in that folder
already. Then ask the questions one at a time, in the order of this page. The order matters. An
earlier answer can change what a later question offers, and some questions are asked only after a
certain answer.

### The user sees where they are

Every question starts with its number and the total, for example `8/47 Q-FOLLOW-UP`. The number is
the count of questions answered so far, plus one. The total is the number of questions that still
apply with the answers so far. When an answer makes questions unnecessary, the total goes down, and
the next question shows the smaller number. For example, a user who keeps their own backend
(`Q-BACKEND`) is not asked the questions of
[The backend the skill creates](#the-backend-the-skill-creates). A question skipped this way counts
neither as answered nor in the total.

### Every answer is saved at once

Before the first question, create the folder of the UI repository and write `INTERVIEW.md` into it.
After each answer, write the answer into the file before you ask the next question. So the user can
stop at any time and go on later, also in a new session, and no answer is lost.

The file has a short head and one section per question, in the order of this page:

```markdown
# Interview

Reference: 1.0.0
Started: 2026-11-17
Last answer: 2026-11-18

## Q-FRAMEWORK

Which UI framework does the cockpit use, and which version?

Answer: Vue 3.5

## Q-TASK-INFORMATION-AREA

Not asked, because `Q-TASK-PAGE-AREAS` has no area `information`.
```

`Reference` is the version of [reference-1.0.0.md](reference-1.0.0.md), the checklist of this
version of the skill. A question that is not answered yet has no section. A question skipped
because of an earlier answer gets a section that says so, with the reason.

### Going on later

At the start, look for `INTERVIEW.md` in the folder of the UI repository. If it is there, read it.
Tell the user how many questions are answered and which question comes next. Then go on with the
first question of this page that has no section in the file. Do not ask a question again that has
an answer.

The user may change an earlier answer at any time. Write the new answer into the file. Then look at
every question whose condition or choices depend on it: ask a question again whose choices
changed, and ask a question marked "Not asked" whose condition holds now.

Generate nothing before every question that applies has an answer in the file.

### Check an answer before you save it

An answer that is unclear or does not fit the others comes back as an open question later, in the
middle of the work. Settle it while the user is still there.

- **A version against the other versions.** When the user names a library for a framework, ask npm
  which framework versions each release of the library supports, before you save the answer:

  ```bash
  npm view <package> versions --json
  npm view <package>@<version> peerDependencies
  ```

  If no release supports the version of `Q-FRAMEWORK`, say so at once and let the user choose:
  the framework version the newest release supports, another library, or no library. For the
  framework itself, propose a version that is in active support and that the libraries named so
  far support, not an older one.

- **A list whose order matters.** When the user gives columns or another ordered list and leaves
  the place of an item open, read the whole list back in the order you understood, and save it
  only after the user has said yes.

- **A placeholder.** When the user answers a name, a coordinate or an address with a placeholder,
  such as `com.example`, `@example` or "later", save it with the word `Placeholder:` in front.
  At the end of the interview, list every placeholder and the question it belongs to, and ask once
  whether the user wants to give the real values now. A placeholder the user keeps is a decision,
  not an open question of the work later. Name the placeholders again in the report at the end of
  the work, with the files that hold them.

- **A feature the GUI API cannot serve.** Some wishes need data the GUI API does not give, for
  example a count narrowed to a date range. Tell the user what the API can do, see
  [gui-api.md](gui-api.md), and save the choice they make, not the wish.

### A newer version of the skill

The question ids are the key, not the numbers. A newer version of this skill may add questions, and
the file names the reference it was written with. Compare the ids in the file with the ids on this
page. Ask each question that has no section, wherever it stands in the order; it counts in the
number and in the total like any other. An id that the file has and this page no longer lists stays
in the file, and you do not ask it. Then write the new reference version into the head. The same
holds when you upgrade a generated user interface, see
[Upgrading a generated user interface](../SKILL.md#upgrading-a-generated-user-interface).

| `Q-AVATARS`       | Are there pictures of persons (avatars)? Without them, every person shows as a round badge with the initials of the name. Use the word from `Q-WORDING` in every text of the generated user interface: the toggle in the
header, the list, the page, the messages, the menu. This description says "case" throughout.

Then ask what a case kind is (`Q-CASE-KIND`). Ask it right after `Q-WORDING`, with the word just
chosen, and explain first why it is asked:

> The cockpit groups cases by their kind: in a column "case kind" of both lists, in its filter, and
> in a chart of the dashboard. VanillaBP has no field of its own for the kind, so we pick one of the
> fields the workflow modules report. Which one fits depends on how your processes are named.

Then offer the three answers:

- `bpmnProcessId`, the id of the BPMN process, for example `LoanApproval`. It is always there. It
  fits when the ids are short and readable for a user. This is the default.
- the case title, `workflowTitle` in the task list and `title` in the case list, a text per
  language. It fits when the workflow modules report the same title for every case of a kind, for
  example "Loan approval". It does not fit when the title names the single case, for example
  "Loan of Mrs Meier", because then every case is a kind of its own.
- a short code below `details`, by default `details.caseKind`, for example `LOAN`. It fits when
  neither of the two does. Tell the user what it costs: every workflow module has to report this
  key, on the case and on each of its user tasks, so it is an agreement with the authors of the
  modules. A case or user task without the key has no kind; it shows an empty cell and counts as
  "other" on the dashboard.

Save the field, and for the code the key below `details`. The column, its filter and the chart of
the dashboard all use it, see
[behaviour.md](behaviour.md#the-fields-behind-the-fixed-columns).

`Q-AVATARS` only asks whether there are pictures. Where they come from and how long they are kept
is asked with the backend the skill creates, in `Q-AVATAR-SOURCE` and `Q-AVATAR-CACHE`. With the
answer no, those two are not asked and do not count in the total.

| `Q-BACKEND`            | Shall the skill create the backend repository, or does the organisation keep a backend of its own? The skill creates a Spring Boot application on the `business-cockpit` library, with the controllers of the lists, the login, the user directory, a module `types` for the types jar and a `docker-compose.yaml`, see [backend.md](backend.md). Ask `Q-BACKEND` before `Q-BUILD-TOOL`. With a backend of the organisation's own, its build files
answer `Q-BUILD-TOOL`, and the user only confirms it.

Ask `Q-LOGIN-KIND` and `Q-TOKEN` before `Q-HOSTING`. The login and the place of the token decide
whether the user interface has to load before the login.
